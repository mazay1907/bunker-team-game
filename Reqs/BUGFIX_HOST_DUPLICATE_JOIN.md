# Bug Fix — Phantom Duplicate Player on Host's Immediate New-Game Create

**Status:** Ready for Developer
**Priority:** High (data integrity / room-size correctness — regression of a just-shipped fix)
**Reported by:** QA, static trace during BUG-1 verification
**Confirmed by:** QA (root cause) + Solution Architect (fix scope sign-off below)
**Regression source:** Side effect of `Reqs/BUGFIX_SESSION_ROOM_SCOPING.md` (BUG-1) — the server's new room-code-match check on reconnect (correctly) rejects a stale token, which then falls through into an unguarded first-time-join path.
**Revision:** v3 — revised after QA flagged a factual error in v2's Scenario G reasoning (dual-tab cookie-sharing premise); see "QA Findings Addressed in v3" at the bottom for a change log against v2.

---

## 1. Problem Statement

When a host finishes a game and immediately creates a new game in the same browser tab, the new room ends up with a phantom duplicate player: the host's real nickname (e.g. `"1111"`) appears twice in the player list — once as the crown-holder host row (server-inserted at room creation, never attached to a socket), and once as `"1111 (2)"` (a second row created via the normal join path, holding the real live socket). The room's player count is off by one. Players joining a room normally (not immediately after finishing a previous game in the same tab) are unaffected.

## 1a. Confirmed Root Cause (QA static trace + SA code read — do not re-derive)

1. `POST /api/rooms` (`packages/server/src/services/RoomManager.ts:70-121`) inserts the host into `room.players` immediately, with `socketId: null`.
2. The client's Socket.IO socket object from the just-finished PREVIOUS game is still connected in the same tab (neither `GamePage.tsx`'s "На головну" button at line 905 nor the SPA's `navigate('/')` disconnects it). `HomePage.tsx`'s `handleCreateRoom` (line 78) calls `socket.connect()` unconditionally, with no `if (!socket.connected)` guard — but since the socket is already connected, this is a Socket.IO no-op. No fresh handshake occurs, so the `auth` callback (`socket.ts` ~lines 78-90) never re-evaluates against the newly-set `activeRoomCode`; the live connection still carries whatever tokens were captured at its last real handshake (the OLD room's).
3. The client emits `ROOM_JOIN` for the NEW room. Server's `roomHandlers.ts` reconnect branch resolves the stale `reconnectToken` (if any survives on the handshake) to the OLD room; BUG-1's `roomMatches` check (`found.room.roomCode !== roomCode`, ~lines 88-112) correctly rejects it as a valid reconnect — `isReturning = false`. This part is BUG-1 working as designed.
4. Falls through to the first-time-join path (`roomHandlers.ts:186-277`). `existingNicknames` (~line 248-250) is built from the NEW room's `room.players` — which already contains the pre-inserted host row from step 1. `RoomManager.uniqueNickname()` (lines 128-135) sees a collision on the host's own nickname and mints `"<nickname> (2)"`.
5. A second `Player` row is inserted with the real socket attached. Result: two rows for the same human — host crown on the orphaned no-socket row, room size off-by-one.

**Solution Architect confirmed this same failure pattern is not unique to `HomePage.tsx`.** `LobbyPage.tsx`'s `doJoin()` (line ~199) has an `if (!socket.connected)` guard, but that guard solves a *different* problem (avoiding a redundant `.connect()` call) — it does nothing to force a fresh handshake when a socket is already connected to a stale room and the user opens a fresh invite link for a different room in the same tab. SA confirmed this is in scope as the same bug class, not a separate issue.

## 2. Expected Behavior (Acceptance Criteria)

**A. Host finishes game, immediately creates a new game (primary repro)**
Given a host is on the game-over screen of room `Y9E3XX` and clicks "На головну," and then immediately creates a new room via `HomePage`, when the new room `ZZP7J6` is created and the host lands in its lobby, then the player list shows exactly one row for the host, holding the host crown, with the socket attached — no `"<nickname> (2)"` row, and `room.playerCount` matches the actual number of distinct humans present.

**B. Host uses back-button after game-over, then creates/joins another room**
Given a host navigates back (browser back button) from the game-over screen or from `HomePage` after a finished game, and then creates a new room or joins an existing one via a fresh invite link, in the same tab, when the new room is entered, then the same single-row guarantee as Scenario A holds — no duplicate row, regardless of whether the socket was already connected from the prior room.

**C. Fresh invite link opened in a tab with a stale connected socket (LobbyPage path)**
Given a browser tab's socket is still connected to room `Y9E3XX` (host or any player finished/left that room without a full page reload), and the user opens a fresh invite link for a different, already-existing room `WWWW22` in that same tab (`LobbyPage.tsx`'s `doJoin()`), when the join completes, then the player is added to `WWWW22` as a single row with the correct nickname (or a legitimate `uniqueNickname()` suffix only if a DIFFERENT human already holds that nickname in `WWWW22`) — never a duplicate of an existing un-socketed row belonging to the same session.

**D. Server rejects duplicate-row creation even if a client-side fix is incomplete (defense in depth)**
Given the server receives a first-time-join `ROOM_JOIN` for a room, and the incoming `sessionToken` matches an existing player row in that SAME room that has `socketId === null` and `status === 'ACTIVE'` (i.e., an HTTP-pre-inserted row not yet attached to any socket), when the server processes this event, then it MUST attach the incoming socket to that existing row (`socketId`, `socket.data.playerId`, room join) instead of creating a new row via `uniqueNickname()` + insert — regardless of what nickname was sent in the payload. This must hold even in a hypothetical scenario where the client-side connect/reconnect fix (Scenarios A-C) has a bug or is bypassed (e.g., a manually crafted `ROOM_JOIN` for testing) — the server is the final guarantee against duplicate rows for the same session.

**E. Normal join/reconnect flows are unaffected (no regression)**
Given any of: a brand-new player joining a room for the first time with a genuinely new session, a player refreshing the page and reconnecting via `reconnectToken` (S5-1 mechanism), a kicked player rejoining by nickname, multi-tab session-claim (`BroadcastChannel`), or two DIFFERENT humans who happen to share a nickname in the same room, when these flows run, then they behave exactly as they do today — Scenario D's sessionToken-attach check only fires for the narrow "un-socketed row in the exact same room, matching sessionToken" case, and never intercepts or alters `uniqueNickname()`'s behavior for genuine nickname collisions between different people.

**F. Disconnect/connect ordering race (old room's disconnect vs. new room's connect)**
Given the client-side connection-hygiene mechanism (`ensureConnectedForRoom()`, Section 3) determines a forced re-handshake is required (socket is connected but last-handshaked for a different room), when it executes `disconnect()`, then it MUST await either the socket's own `'disconnect'` event or a ~500ms timeout fallback (whichever fires first) BEFORE calling `connect()` for the new room — the function must never call `connect()` synchronously back-to-back with `disconnect()` in the same tick. Expected outcome: by the time the new room's `connect()`/handshake fires, the previous connection has either fully closed (normal case) or the timeout fallback has elapsed (defensive case, e.g. a slow/lost server ack of the close), so the new handshake's `auth` callback always evaluates against a clean state, not a half-torn-down previous connection. This holds regardless of network latency between client and server.

**G. Dual-tab does not cause cross-tab session misattachment**
Given Tab 1 has a socket still connected to just-finished room `Y9E3XX` (no navigation away in that tab), and — concurrently or shortly after — Tab 2 (a different tab, same browser/session) creates a new room `ZZP7J6` via `HomePage`, when Tab 2's socket completes its `ROOM_JOIN` for `ZZP7J6`, then: the server's Scenario D sessionToken-attach check MUST attach Tab 2's socket (and only Tab 2's socket) to `ZZP7J6`'s pre-inserted host row — Tab 1's leftover socket must never be attached to `ZZP7J6`'s row, and must never affect `ZZP7J6`'s player list at all. Note: cookies are shared across all tabs of the same origin (`document.cookie` is per-origin, not per-tab), so Tab 1 CAN read `ZZP7J6`'s cookie the instant Tab 2 sets it — safety does NOT come from cookie exclusivity. See Section 4's corrected Solution Architect note for why this is still structurally safe. No additional server-side check (e.g., a connection nonce) is required.

## 3. Constraints

- **Must NOT reopen BUG-1's regressions.** The `roomMatches` check on the reconnect branch (`roomHandlers.ts` ~lines 88-112), the room-scoped cookie keys (`sessionKey`/`reconnectKey`), and the `setActiveRoomCode()` contract in `socket.ts` must remain exactly as BUG-1 shipped them. This fix's server-side check (Scenario D) is additive and sits in the first-time-join path only, after the reconnect branch has already been tried and failed — it never changes reconnect-branch behavior.
- **Must NOT break normal join/reconnect.** Same-room refresh reconnect (S5-1), kicked-player rejoin, name-based reconnect fallback (`roomHandlers.ts` ~lines 198-235), and multi-tab session-claim must all continue to work unchanged (see Scenario E).
- **`uniqueNickname()` must still fire for genuine nickname collisions** between two different humans in the same room — the sessionToken-based attach check (Scenario D) is keyed on session identity, never on nickname alone.
- **Client-side fix MUST use a single shared, mandated mechanism — not three ad-hoc guards.** `socket.ts` must export:

  ```
  export async function ensureConnectedForRoom(roomCode: string): Promise<void>
  ```

  This exact function (name and contract below) is a requirement of this spec, not an illustrative example — `HomePage.tsx`'s `handleCreateRoom` (replacing its inline block ~lines 74-85), `LobbyPage.tsx`'s `doJoin()` (replacing ~lines 197-206), and `GamePage.tsx`'s two reconnect mount effects (replacing ~357/384-391 and ~556-565) must all call it instead of their own inline `if (!socket.connected) { socket.connect(); await ... }` logic. Per Solution Architect sign-off, its contract is:
  - Maintain a new module-level `lastHandshakedRoomCode: string | null` (parallel to the existing `activeRoomCode` from BUG-1 — `activeRoomCode` is "intent," `lastHandshakedRoomCode` is "what the live connection actually completed a handshake for") plus an in-flight guard (`inFlight: Promise<void> | null`, `inFlightRoom: string | null`) to make concurrent calls for the same target room (e.g., React StrictMode double-invoke) collapse onto the same promise rather than starting a second disconnect/connect cycle.
  - Normalize `roomCode` to uppercase before comparing/storing.
  - **No-op branch:** if `socket.connected && lastHandshakedRoomCode === roomCode`, return immediately — nothing to do.
  - **Fresh-connect branch:** if `!socket.connected` (first mount, or the socket already dropped, e.g. tab close/reload), call `setActiveRoomCode(roomCode)`, `socket.connect()`, await the existing `'connect'`/`'connect_error'` race with its current ~5s timeout (same pattern already used inline in all three call sites today), then set `lastHandshakedRoomCode = roomCode`.
  - **Force-rehandshake branch (the actual bug fix):** if `socket.connected && lastHandshakedRoomCode !== roomCode` (a stale-room socket reused for a different target room — the BUG-2 repro path), call `setActiveRoomCode(roomCode)`, then `socket.disconnect()`, then await either the socket's `'disconnect'` event or a ~500ms timeout fallback (see Scenario F — never call `connect()` synchronously back-to-back with `disconnect()`), then `socket.connect()`, await the same `'connect'`/`'connect_error'` race as the fresh-connect branch, then set `lastHandshakedRoomCode = roomCode`.
  - Rejects/throws on connect timeout or `connect_error`, exactly like each call site's current inline promise, so existing `try/catch` blocks at each call site need no behavioral change beyond swapping in the new call.
  - Each call site's separate, redundant `setActiveRoomCode()` call immediately preceding its old inline connect block should be removed — `ensureConnectedForRoom()` now owns that call internally.
  - **In-flight queuing contract (generalizes the StrictMode same-room collapsing above to the different-room case):** a call arriving for a DIFFERENT room while a cycle is already in-flight must be QUEUED, not collapsed and not run concurrently — overlapping disconnect/connect on the single Socket.IO singleton is unsafe (same race class as Scenario F, worse when two cycles interleave). Concrete contract, using the `inFlight: Promise<void> | null` / `inFlightRoom: string | null` state already declared above:
    - If `inFlight` exists and `inFlightRoom === roomCode`: return the existing `inFlight` unchanged (same-room collapsing, as already specified).
    - If `inFlight` exists and `inFlightRoom !== roomCode`: set `inFlight = inFlight.catch(() => {}).then(() => runCycle(roomCode))` and return that new promise — i.e. chain/queue behind the in-flight call, evaluating `lastHandshakedRoomCode` fresh only after the prior call has settled.
    - Two cycles must never run concurrently; at most one disconnect/connect cycle is in flight at any time, and different-room requests serialize through the queue in call order.
- **Server-side check (Scenario D) is mandatory, not optional** — per Solution Architect sign-off, this is a server-authoritative game (CLAUDE.md: "All game logic lives on the server. The client is a dumb view.") and a duplicate-player-row defect is a server data-integrity failure that must not be preventable-only-by-client-correctness.

## 4. Solution Architect — Technical Sign-Off (for Developer reference)

- **Both client-side (connection hygiene) and server-side (defense-in-depth) fixes are required.** The client fix prevents the bad case from firing in the normal flow; the server fix is the actual guarantee, independent of client behavior.
- **Concrete server-side mechanism (Scenario D):** in `roomHandlers.ts`, before the "handle nickname collision" block in the first-time-join path (~line 247, using the `room` already resolved via `roomCode`), add a lookup: search `room.players` for an existing row with `socketId === null`, `status === 'ACTIVE'`, and `sessionToken === parsed.data.sessionToken` (the client already sends `sessionToken` in every `RoomJoinPayload` — confirmed in `HomePage.tsx` and `LobbyPage.tsx`). If found, attach this socket to that row (`socketId: socket.id`, `socket.data.playerId = found.playerId`, `socket.join(room.roomId)`) and skip `uniqueNickname()` + new-row creation entirely. This mirrors the existing reconnect branch's `ACTIVE && !socketId` condition (line ~111), applied to the first-time-join path for the specific HTTP-pre-insert gap.
- **Confirmed additional at-risk flow:** `LobbyPage.tsx`'s `doJoin()` — its `if (!socket.connected)` guard solves a different problem (avoiding redundant `.connect()`) and does not force a fresh handshake when a stale-room socket is reused for a different target room. In scope for the client-side fix (Scenario C).
- **Confirmed lower-risk / likely-safe flows (spot-check only, not required to redesign):** tab close + rapid rejoin (socket typically drops on tab close, so this is a genuine fresh reconnect, not the no-op-connect pattern); `GamePage.tsx`'s existing reconnect guards (lines 384, 558) — page reload normally drops the socket entirely, so risk is low, but should be spot-checked during QA regression pass.
- **`roomJoinSchema` (shared Zod schema):** verify `sessionToken` is already consistently typed/required-or-nullable across both the HomePage-create-room flow and the LobbyPage-join flow before relying on it for the Scenario D server check — this is a verification step, not expected to require a schema change.
- **Explicit regression check list for QA:** normal first-time join with a genuinely new session, refresh-reconnect (S5-1), kicked-player nickname rejoin, multi-tab session-claim, and two different humans sharing a nickname in one room — none of these should be altered by the Scenario D addition.
- **Ordering race (Scenario F) — confirmed mandate:** Socket.IO's client-side `disconnect()` sets local `connected = false` synchronously, but the underlying transport close and the server's receipt of it are asynchronous over the wire. Calling `connect()` synchronously back-to-back with `disconnect()` is not documented as guaranteed-safe sequencing and would risk reintroducing a subtler variant of this same bug class (a handshake racing a not-yet-completed teardown). `ensureConnectedForRoom()`'s force-rehandshake branch must explicitly await the `'disconnect'` event (with a ~500ms timeout fallback, in case the event never fires) before calling `connect()`. This costs at most ~500ms and removes the ambiguity. Note this ordering concern is orthogonal to the primary repro (Scenario A) — since old-room and new-room are different `roomCode`s, the server's `roomMatches` check (BUG-1) already isolates them regardless of cleanup timing; this mandate is about determinism/testability of the client mechanism itself.
- **Dual-tab misattachment (Scenario G) — confirmed no additional server check needed, corrected reasoning.** Cookies are shared across all tabs of the same origin (`document.cookie` is per-origin, not per-tab) — Tab 1 can read `ZZP7J6`'s cookie the instant Tab 2 sets it. Safety does not come from cookie exclusivity. It comes from two facts: (1) `activeRoomCode`/`lastHandshakedRoomCode` are per-tab JS module bindings with no cross-tab sync in this codebase (`BroadcastChannel` only compares values, never assigns them), so Tab 1's own state is never mutated by Tab 2, and no code path in Tab 1 ever constructs `roomCode: 'ZZP7J6'` in a `ROOM_JOIN` emission unless Tab 1 itself navigates there (collapsing into Scenario A/B/C); (2) even in a hypothetical bug where Tab 1 emitted `roomCode: 'ZZP7J6'`, Scenario D's server-side match requires the incoming `sessionToken` to belong to a row inside the room resolved by that `roomCode` — since tokens are `randomBytes(32)` minted per (room, player) pair and never reused across rooms, no cross-room token can ever match. No connection nonce or tab-id is warranted.
  - Supporting detail: each tab is a separate JS module-graph instance, so `activeRoomCode` is physically a different variable per tab. The `auth` callback closure reads the live binding at handshake time (socket.io-client re-invokes `auth` on every connect/reconnect attempt, including automatic retries), so it's never stale — but "fresh" means fresh against THAT tab's own state, which only that tab's own app code (via `setActiveRoomCode`, sourced from `useParams`/that tab's own HTTP response) can change.

## QA Findings Addressed in v2

This revision closes the following gaps identified by QA's review of v1:

1. **Incomplete regression-safety list (FAIL item 1)** — Section 5's BUG-1 regression checklist now includes Scenarios **A** and **C1** from `BUGFIX_SESSION_ROOM_SCOPING.md`, in addition to the previously-listed B, D, E, F, G, H. C1's repro path ("play a full game to completion in room X, host starts a new game producing room Y ... no leftover players/character/nickname/vote state from room X is visible") is nearly identical to this spec's own Scenario A, making it the regression most likely to interact with this exact fix.
2. **Connection-hygiene mechanism was illustrative, not mandated (FAIL item 2)** — Section 3 now mandates a concrete, named function, `ensureConnectedForRoom(roomCode: string): Promise<void>`, exported from `socket.ts`, with a fully specified contract (module-level `lastHandshakedRoomCode` state, in-flight/StrictMode guard, no-op / fresh-connect / force-rehandshake branches). All three call sites (`HomePage.tsx`, `LobbyPage.tsx`, `GamePage.tsx`) are required to call this exact function instead of writing their own inline guards. Confirmed by Solution Architect consultation.
3. **Missing race-condition scenarios (FAIL item 3)** — added Scenario F (disconnect/connect ordering: `ensureConnectedForRoom()`'s force-rehandshake branch must await the `'disconnect'` event or a ~500ms timeout fallback before calling `connect()`, never back-to-back in the same tick) and Scenario G (dual-tab: confirmed, per Solution Architect, that no additional server-side check beyond Scenario D's existing same-room + sessionToken match is needed, because room-scoped cookies and per-room-random `sessionToken`s already make cross-tab misattachment structurally impossible). Both have matching DoD checkboxes and Section 4 sign-off notes.

## QA Findings Addressed in v3

This revision closes a factual error QA identified in v2's Scenario G reasoning:

1. **Scenario G premise was false (QA FAIL)** — v2 argued "Tab 1 never holds `ZZP7J6`'s room-scoped session cookie" as the reason cross-tab misattachment is impossible. This is factually wrong: `document.cookie` is per-origin, not per-tab, so Tab 1 CAN read `ZZP7J6`'s cookie the instant Tab 2 sets it. This premise also contradicted the app's own `BroadcastChannel` session-claim mechanism, which exists precisely because cross-tab cookie/session conflicts are real. Corrected, per Solution Architect re-analysis: safety comes not from cookie exclusivity but from (1) `activeRoomCode`/`lastHandshakedRoomCode` being per-tab JS module bindings with no cross-tab sync (`BroadcastChannel` only compares values, never assigns them), so Tab 1's own state can never construct a `ROOM_JOIN` for `ZZP7J6` unless Tab 1 itself navigates there, and (2) even in a hypothetical bug where Tab 1 did emit `roomCode: 'ZZP7J6'`, Scenario D's server-side match requires the incoming `sessionToken` to belong to a row inside that exact room, and tokens are `randomBytes(32)` minted per (room, player) pair and never reused across rooms. Section 4's Scenario G note, Section 4a's supporting detail, and the Scenario G acceptance criterion (Section 2) have been rewritten to reflect this corrected reasoning. The conclusion (no additional server check needed) is unchanged — only the justification was corrected.
2. **Generalized the in-flight queuing contract in Section 3** — the existing same-room StrictMode-collapsing behavior (`inFlight`/`inFlightRoom`) is now explicitly extended to the different-room case: a call for a different room while one is in-flight is queued (chained behind the settled prior promise via `inFlight = inFlight.catch(() => {}).then(() => runCycle(roomCode))`), never collapsed and never run concurrently with the in-flight cycle — preventing overlapping disconnect/connect cycles on the single Socket.IO singleton (same race class as Scenario F). Added a matching DoD checkbox.
